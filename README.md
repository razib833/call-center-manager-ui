# Local Manager database testing

The Manager Portal uses the same `DESKTOP-BUDV4V7 / JamunaCustomer360` database as the Agent API. Its separate development API listens on port 7247; the Agent API on 7246 is unchanged. Run the launcher as your existing Windows deployment account (Risha), which can impersonate the database test user.

Double-click `Start-Manager-Portal.bat` in the avaya-screen folder. The LIVE launcher opens http://127.0.0.1:5175/manager/pending; the old MOCK server on 5174 may stay open. Sign in with **manager@local.test** / **Manager@Test123!**. The fixed login is verified by the local backend and issues a Manager session cookie; it is not a frontend authentication bypass. This development host refuses non-Development environments. The Manager and Agent API use distinct cookies.

`Server` compiles the existing API contracts/controllers together with a local Manager entry point, password authenticator, and SQL executor. No Agent Portal or shared API source is edited. Every SQL connection executes as `Customer360_LocalManager` and verifies its identity and `Customer360_ManagerExecRole` membership. The Windows connection needs permission to impersonate this no-login database user; do not run the application under the restricted Agent Windows account. This is a local development arrangement, not a production identity setup.

`SetupManagerDatabase.sql` is the standalone SSMS script. Run the entire script as the existing local database owner if setup is needed. It adds the no-login Manager test principal to the existing procedure role and adds 36 synthetic tickets: 24 pending, 6 approved and 6 rejected, with all four priorities, histories and overdue/future SLAs. Re-running it does not reset decisions or duplicate ticket numbers. It does not alter existing tickets or enqueue notifications. These fixtures do not include public tracking tokens.

The backend workers remain disabled. A rejection performed through the actual Manager workflow can enqueue a synthetic notification according to the existing LOCAL_DEV_TEST service configuration. Keep workers disabled for this test database. The three pre-existing tickets remain visible because this is the shared database; use ticket numbers prefixed `MGRTEST-` for testing.

Logs are in `ManagerPortal/TestResults/Live`. Keep the launcher window open; press Enter to stop its two Manager processes. If port 5175 is occupied by another LIVE Manager instance, stop that instance first. Node.js, .NET 10 SDK, SQL Server and a Windows account with the existing local database access are required. Dependencies are restored and the Manager API is built at startup; no test data is inserted automatically by the launcher.

Validation: Manager frontend 23/23 tests passed; TypeScript and production build passed (dependency use-client warnings). Separate Manager API built with zero warnings/errors. Live login rejected the wrong password, accepted the fixed credentials, read SQL queue/dashboard/references/history, and persisted rejection of MGRTEST-023 and approval of MGRTEST-024. Synthetic fixture counts after these checks: 22 pending, 7 approved, 7 rejected. The 3 original tickets were unchanged. The launcher readiness check passed on web port 5175 including the API proxy and cleaned up its two processes. Table SELECT and Agent ticket-create permissions were both denied; Manager approve permission was granted.
